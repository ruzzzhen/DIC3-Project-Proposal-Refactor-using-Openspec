## Q1. 五個核心思維模式（5 Cores）

### Core 1｜「正常」必須有條件，不能只用全期平均

- **意義：** 同樣的用電量，放在不同季節、星期、時段與使用方式下，可能代表完全不同的狀態。偏離要相對於「可比較的條件」來算。
- **證據：** IEA 把天氣列為 2025 年用電變化的因素之一 [D1]。DOE FEMP 的 M&V 方法要求以天氣、使用等獨立變數調整基準 [D8]。Granderson 等人以 537 棟商業建築測試十種以區間電表資料建立的自動化基準模型，顯示這類基準在 12 個月訓練資料下的中位數 CV(RMSE) 皆低於 25%，說明「以歷史同條件資料建基準」在實務上可行 [D11]。
- **如何影響系統設計：** 以同星期×小時中位數 B1 作為主要基準，並保留全域中位數 B0 作為對照，讓「條件」的價值可以被 RQ1 檢驗。報告必須回傳比較群組、樣本數與天氣背景。對應 spec：`analytics-engine › Train-only baselines`、`domain-knowledge › Historical deviation rule`。

### Core 2｜先辨識資料問題，再討論營運異常

- **意義：** 缺值、零值與尖峰可能是量測或傳輸問題，也可能是真實的營運變動。全部刪掉或全部當成故障，都會扭曲結果。
- **證據：** BDG2 維護者明列 cleaned 版本的移除規則：S-H-ESD 偵測的離群值、連續超過 24 小時的零值、電表的絕對零值 [D6]。BDG2 原始論文也指出資料具異質性與缺漏 [D3]。
- **如何影響系統設計：** 以 raw 作為主要輸入，品質閘門排在分析之前；不補零，衝突值遮罩；有效率不足就回傳 INSUFFICIENT_DATA。對應 spec：`data-retrieval › Unit and time-axis gate`、`Coverage threshold gate`、`No zero-filling and conflict masking`。

### Core 3｜可解釋的統計偏離，不等於設備根因

- **意義：** 「夜間高於歷史基準」是可驗證的觀察；「冷氣忘記關」則需要排程、設備狀態或現場紀錄。同一條總表曲線可能由多個設備組合產生。
- **證據：** DOE FEMP 明言整棟建築的 Option C 無法驗證個別措施的成效 [D8]。用 LLM 查詢 BAS 時序的研究中，模型仍會遺漏感測器、自行假設異常門檻 [A4]。
- **如何影響系統設計：** 報告採五段式：觀察 → 基準 → 假說 → 尚缺證據 → 下一步。禁止從總表確診設備故障；評估另計「未支持根因斷言數」。對應 spec：`decision-recommendation › No root-cause diagnosis from whole-building meter`。

### Core 4｜分析的價值要經過管理者行動才可能形成效益

- **意義：** 實務上關心的不是找到多少異常點，而是能否把有限的查核時間花在值得處理的事件上。連續 20 小時的同一現象若拆成 20 則警報，只會增加負擔。
- **證據：** LBNL Smart Energy Analytics Campaign 涵蓋 104 個組織、約 6,500 棟建築，EIS 與 FDD 使用者的年節能中位數分別為 3% 與 9% [D7]。這是計畫實績，不能移植為本專題的預期節電率。
- **如何影響系統設計：** 相鄰同向的警示點合併為事件，每則建議附持續時間、偏離量與下一步查核。「減少調查時間」必須經過計時實驗才能主張。對應 spec：`analytics-engine › Same-direction event grouping`、`decision-recommendation › Five-part recommendation structure`。

### Core 5｜公開基準提高可重現性，但不保證跨建築有效

- **意義：** 可下載的共同資料讓方法可以互相比較；但不同建築、氣候與年代可能需要不同的基準。對資料集有效，不等於能直接部署到臺灣校園。
- **證據：** BDG2 涵蓋 19 個場址、1,636 棟非住宅建築、3,053 個各類計量表 [D3]。建築時序基礎模型研究顯示，本地調整與上下文長度會影響預測品質 [D9]。
- **如何影響系統設計：** 最低版本只做單棟、按時間切分，訓練／校準／測試不重疊。跨建築泛化與臺灣適用性明列為未驗證的限制。對應 spec：`analytics-engine › Chronological split with isolation`。

## Q2. 三個專業爭論（3 Trade-offs）

> 這三項是與「建築用電調查」直接相關的爭點；沒有證據能將它們排名為全領域最激烈的前三名。

### Trade-off 1｜積極清理資料 ↔ 保留可疑原值

- **觀點 A（積極清理）：** 量測錯誤會污染「正常」基準，清理後的輸入較一致，有利於預測建模。
- **觀點 B（保留原值）：** 對異常研究而言，被清掉的尖峰與長零值可能正是要找的現象。
- **Evidence：** BDG2 同時提供 raw 與 cleaned，並公開清理規則（S-H-ESD 離群值、>24 小時零值等）[D6]。LEAD 資料集以 BDG2 為基礎人工標註異常，說明異常研究需要保留可疑原值 [D10]。
- **Consensus：** 至少要保留版本、品質旗標與處理理由，不能以清理後的資料冒充完整觀測。
- **Unresolved：** 沒有現場紀錄時，哪些值是真故障、哪些是營運改變或感測器問題，仍無法判定。
- **對本系統的影響：** 主要分析使用 raw 加上品質旗標；cleaned 只作為另行標示的敏感度分析（spec：`data-retrieval › Raw meter data as primary input`）。

### Trade-off 2｜通用預訓練／基礎模型 ↔ 目標建築本地模型

- **觀點 A（通用模型）：** 時序基礎模型可以零樣本使用，減少逐棟訓練的負擔，也有機會跨區域遷移。
- **觀點 B（本地模型）：** 建築的用途、季節與占用差異大，以目標資料訓練或微調通常更準，也更容易解釋。
- **Evidence：** Park 等人以 Chronos 在日本 SUSTIE 商業建築上比較零樣本、全量微調與 LoRA。結果顯示短上下文的零樣本表現落後，微調可以改善；增加上下文也有助於零樣本預測 [D9]。Mulayim 等人評估時序基礎模型（TSFM）於建築能源管理任務，發現在未見過的資料上僅「略優於統計模型」，且加入共變量不一定有幫助 [A8]。反之，HVAC 故障診斷研究顯示，以標註資料微調的領域 LLM 明顯優於通用模型 [A9]，但這需要總表資料所沒有的故障標籤。
- **Consensus：** 比較時必須使用相同資料與預測範圍，並一併報告上下文長度、訓練與計算成本；目前沒有在所有條件下都勝出的模型。
- **Unresolved：** 多少本地資料、多少計算成本才值得做調整？跨建築結果能否外推？
- **對本系統的影響：** 最低版本採逐棟中位數基準，可重現、成本低且可解釋；基礎模型列為後續擴充，不承諾實作（spec：`analytics-engine › Train-only baselines`）。

### Trade-off 3｜LLM 自由生成解釋 ↔ 工具計算＋證據驗證的受限 Agent

- **觀點 A（自由生成）：** LLM 能直接閱讀資料與圖表、產生流暢解釋，彈性高，開發成本低。
- **觀點 B（受限、可驗證）：** 數值應由工具計算，LLM 只負責規劃與敘述，所有主張都要能回查證據。
- **Evidence：** ReAct 顯示交替「推理–動作–觀察」能取得外部事實，但也會陷入重複動作或受檢索失敗影響 [A1]。BAS 查詢研究中，GPT-4o 在三個問題各五次的測試裡，氣流下降題只成功 3/5，並出現查詢錯誤與遺漏感測器 [A4]。Argos 以「LLM 產生可執行規則、再經審查」的方式取得可重現的偵測 [A2]。Zhou 與 Yu 在 ICLR 2025 的研究指出，明確要求 LLM 推理並不能改善時序異常偵測，也沒有證據顯示 LLM 能理解細微的真實異常 [A6]。He 與 Jazizadeh 的建築能源 Agent 原型在「能源分析」類問題的回答正確率為 77%、成本估算僅 49% [A7]。2026 年針對 66 篇 HVAC LLM 研究的回顧發現，僅 4 篇達到試點層級證據，沒有任何一篇回報持續運轉部署 [A10]。
- **Consensus：** 數值計算交給確定性的程式，LLM 的輸出需要可檢查的中介，例如規則、工具紀錄或證據 ID。
- **Unresolved：** 結構驗證只能檢查 ID、數值與單位，因果語意是否被正確支持仍需人工審閱；Agent 相對固定流程是否真有額外價值，也還沒有答案。
- **對本系統的影響：** 採工具白名單、10 次預算、證據驗證與模板降級，並以「固定報表／固定流程＋LLM／Agent」三組比較來檢驗 Agent 的增益（spec：`output-interaction › Reference and number validation`、`offline-evaluation › Three-group fair comparison`）。

## Q3. 十個深度理解問題（10 Details）與參考答案

> 參考答案是口試用的判讀要點，不是唯一解。題型標籤對應課程要求的推理層次。

| # | 題型 | 問題 | 參考答案（要點） |
|---|---|---|---|
| 1 | **Why** | 為什麼主要基準選「同星期×小時中位數」，而不是全期平均或直接用 LLM 判斷？ | 建築用電有強烈的週期，同時段比較才是可比較的條件（Core 1）。中位數對既有的尖峰較穩健。用 LLM 直接判斷無法重現、也無法審計。B0 留作對照，讓這個選擇可以被 RQ1 否證。 |
| 2 | **What-if** | 如果測試期遇上連續寒流，B1 會怎樣？能說已經排除氣溫因素嗎？ | B1 不含天氣，寒流可能造成大量偏高警示。不能說已排除氣溫因素，只能由 weather_context 提供「低溫背景」並建議查核空調紀錄；共現不等於因果。 |
| 3 | **Trade-off** | 把異常門檻從 P99 降到 P95，或把相鄰點合併為事件，各自的代價是什麼？ | 降低門檻會增加警示，可能提高注入命中率，但查核負擔也變重。合併能降低通知量，但會改變事件邊界與延遲的計算方式。沒有真實標籤時，警示率不能當作誤報率。 |
| 4 | **Failure Case** | 電表連續 8 小時為 0，系統應如何處理？補零或刪除會有什麼後果？ | 有效零值是觀測，缺值是未知，兩者不能混淆。zero_run_check 觸發後，先建議核對通訊、停用與供電紀錄，不判定斷電。對缺值補零會憑空製造「突然下降」事件。 |
| 5 | **Evidence** | 報告寫「偏離 240 kWh（evidence E12）」，驗證器只檢查 E12 存在就夠了嗎？ | 不夠。還要比對建築、期間、單位與未四捨五入的值。即使 ID 與數值都正確，因果敘述（例如「空調故障」）仍可能沒有證據支持，需要人工審閱。 |
| 6 | **Comparison** | raw 與 cleaned 跑出的事件數不同，能說 cleaned 偵測較準嗎？ | 不能。cleaned 已把部分離群值與長零值改為缺值 [D6]，警示變少可能只是現象被刪除。必須在同期間追蹤被清理的點，分開分析缺失與事件的變化。 |
| 7 | **Design Decision** | 天氣缺漏時，為什麼不中止整個調查？ | 用電歷史比較不依賴天氣；只停用需要天氣的規則，並在報告中標註限制即可（spec：Weather alignment with graceful degradation）。反之，若單位或用電本身不足，就必須停止分析。 |
| 8 | **Real-world Scenario** | 管理者問「哪台空調壞了？上個月省了多少電？」Agent 應該怎麼回答？ | 說明總表證據不足以定位設備；節電需要介入前後量測與調整後的基準（M&V，[D8]）。只能提供偏離量、時段，以及需要調閱的 BAS、工單與排程紀錄（案例 C10）。 |
| 9 | **Comparison** | 若 Agent 的報告比固定流程＋LLM 更好，增益一定來自 Agent 規劃嗎？ | 不一定。三組共用 B1 與相同工具，差異才可能歸因於規劃；也要排除只是提示詞或文字表達造成的差異。若兩者完整度相同而固定流程較便宜，就應建議固定流程。 |
| 10 | **Why / Evidence** | 沒有現場故障標籤，為什麼不報告故障偵測的 precision／recall？用什麼替代？ | 原始資料中可能早已含有真實異常，未警示的點也不等於正常。替代做法是在副本上注入固定擾動，量測命中率與延遲（只代表敏感度），並以人工審閱評估報告品質；兩者必須分開報告。 |

**題型覆蓋檢查：** Why（1、10）、What-if（2）、Trade-off（3）、Failure Case（4）、Evidence（5、10）、Comparison（6、9）、Design Decision（7）、Real-world Scenario（8）——八種推理層次皆已涵蓋。
