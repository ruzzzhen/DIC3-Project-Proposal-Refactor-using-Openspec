# 01 Abstract（A–F 六段式）

> 基礎：[原專案 research/proposal_source.md（tag before-dic3-20261112）](https://github.com/benson103081/energy-detective-agent/blob/before-dic3-20261112/research/proposal_source.md) §1 Abstract。引用編號見 `docs/references.md`。本專題**尚未實作、尚未實驗**，所有成效都是 expected／target。

**題目：** Energy Detective：以受限規劃與證據驗證進行建築用電異常調查的 Domain AI Agent

---

## A. Attention Getter — Motivation

建築是電力需求成長的主角。IEA 估計，2025 年全球用電需求成長約 3%，其中建築部門貢獻了**全年增量的近 45%**（這是增量占比，不是建築占總用電 45%）[D1]。IEA 並預測，2025–2030 年新增用電需求中有 49% 將來自建築 [D2]。目前建築用能約占全球終端能源消費的 30%、全球用電的一半 [D14]。在臺灣，依經濟部能源署官方月資料自行加總，2025 年服務業部門與住宅部門用電分別占全國電力消費的 17.6% 與 19.0%，合計 36.6% [D15]。電表資料早已大量存在，但要從「看到用電變高」走到「知道下一步該查什麼」，仍高度依賴人工判讀。LBNL 的實務計畫顯示，使用能源資訊系統（EIS）與故障偵測診斷（FDD）的組織，年節能中位數分別為 3% 與 9% [D7]。可見分析流程有價值，但這些數字不能移植為本專題的預期成效。

## B. But — Challenge

現有方法有三個缺口：

1. **異常分數無法區分原因。** 單一門檻分不出天氣、營運變化與資料問題；整棟總表也無法驗證個別設備或措施 [D8]。公開資料的清理版本可能已刪掉想研究的異常 [D6]。
2. **LLM 直接判讀數值不可靠。** 明確要求 LLM 推理並不能改善時序異常偵測 [A6]。建築能源 Agent 原型在能源分析類問題上的正確率為 77% [A7]。用 LLM 查詢建築自動化系統時，仍出現查詢錯誤與遺漏感測器 [A4]。
3. **離部署仍遠。** 2026 年一篇回顧檢視了 66 篇 HVAC LLM 研究，只有 4 篇達到試點層級證據，沒有任何一篇回報持續部署 [A10]。

**Research gap：** 對只有建築總表與天氣、沒有設備故障標籤的情境，缺少「數值可重現、主張可回查、且不過度推論」的調查流程及其公平評估。

## C. Cure — Proposed Solution

為解決上述問題，本專題提出 **Energy Detective AI Agent**：一個讓設施管理者以自然語言指定建築與期間，就能取得附**證據 ID、比較基準、待查假說、尚缺證據與下一步查核建議**之調查報告的受限規劃 Domain AI Agent。它的輸出是「值得追查的線索」，不是設備故障確診或已驗證的節電量。

## D. Development — Method

系統依課程八大模組設計（規格見 `openspec/specs/`）：

1. 以 Building Data Genome 2 的 raw 逐時電表、場址天氣與建築中繼資料 [D3] 進行**歷史重播**，模擬 IoT 資料流。
2. **LLM 只負責三件事：** 需求解析、在工具白名單內產生結構化計畫、分析後依觀察做一次規則選擇。
3. **數值全部由 Python 計算：**
   - 品質閘門：單位、時間軸、有效率 ≥ 90%，不補零。
   - 基準：B0 全域中位數，B1 同星期×小時中位數。
   - 異常門檻：校準期絕對殘差的 P99。
   - 事件：相鄰同向的警示點合併為一個事件。
4. **領域知識以四條可檢查的條件式規則實作：** 歷史同時段偏離、非使用時段負載、天氣背景、長段零值。前提不成立時，該規則自動停用。
5. **報告的每個數值都綁定 evidence_id，** 並比對建築、期間、單位與數值。驗證失敗就降級為固定模板。每次執行上限為 10 次工具呼叫、1 次計畫修正、1 次暫時性 I/O 重試。

## E. Experiments — Evaluation（預定）

- **Dataset：** BDG2 單棟 raw electricity，取連續 12 週，依時間切分為 8 週訓練、2 週校準、2 週測試 [D3]。
- **Baselines：**
  - 分析層：B0 對 B1。
  - 系統層：三組比較，即固定 Python 報表、固定流程＋LLM、受限 Agent。三組共用相同資料、工具與 B1 結果。
- **Metrics：**
  - 預測：MAE。
  - 合成擾動：在測試副本注入尖峰、持續增加、連續零值各 10 件，seed = 42，計算注入事件命中率與首次偵測延遲。
  - Agent：任務成功率、事實可追溯率、數值主張正確率、未支持根因斷言數、工具呼叫數、tokens 與秒數。
- **Case study：** 10 個固定案例（C01–C10），涵蓋一般調查、缺建築或期間、資料不足、天氣缺漏、暫時 I/O 失敗、非法工具、要求確診設備。每組方法每案例跑 3 次，共 90 次。
- **評估邊界：** 因為沒有現場故障標籤，**不報告真實故障 precision／recall**。

## F. Findings — Expected Outcomes（尚未實驗，以下皆為 target）

1. **RQ1（待驗證假設）：** B1 在保留測試期的 MAE 低於 B0；若不成立，照實報告並檢討稀疏樣本與營運漂移。
2. **工程驗收目標：**
   - C04–C10 的限制在所有重跑中都不被繞過。
   - 每次執行的工具呼叫 ≤ 10 次。
   - 最終報告的數值主張 100% 可回查證據。
   - 最終報告的未支持根因或節電斷言為 0。
3. **RQ2：** 檢驗受限 Agent 能否在維持必要資訊完整度的前提下，減少不必要的規則評估。結果可能是「固定流程已足夠」，這也是有效結論。
4. **預期產物：** 一份可重現的調查原型、一份一般調查報告、一份資料不足回覆、一張合成擾動比較表。

本階段**不宣稱**提高準確率、證實設備故障或達成節電。
