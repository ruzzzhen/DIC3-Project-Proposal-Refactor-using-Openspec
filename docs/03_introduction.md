## A. Attention Getter（↔ G. General）

建築正成為電力需求成長的主要來源。IEA《Global Energy Review 2026》估計，2025 年全球用電需求成長約 3%，建築部門占全年**增量**近 45% [D1]；《Electricity 2026》預測 2025–2030 年新增用電將有 49% 來自建築 [D2]。目前建築用能約占全球終端能源消費 30%、全球用電的一半 [D14]。

臺灣也不例外。依經濟部能源署「電力消費月資料」自行加總，2025 年服務業部門（17.6%）與住宅部門（19.0%）合計占全國電力消費 36.6% [D15]。

但這些宏觀數字不能證明任何一棟建築正在浪費能源。真正的問題是：**既有電表資料能不能變成值得管理者追查、而且能回到資料核對的調查線索？**

## B. Background（↔ G. General）

- **應用領域：** 建築能源管理。能源管理資訊系統（EMIS／EIS）把電表資料整理成營運資訊；故障偵測與診斷（FDD）則需要設備層級的運轉資料 [D12]。LBNL 的實務計畫涵蓋 104 個組織、約 6,500 棟建築，EIS 與 FDD 使用者的年節能中位數分別為 3% 與 9% [D7]。
- **使用者：** 校園或辦公建築的設施管理者與能源管理人員。這是本專題的情境設定，尚未經過使用者訪談驗證。
- **資料：** Building Data Genome 2（BDG2）。資料來自北美與歐洲 19 個場址、1,636 棟非住宅建築、3,053 個各類計量表，提供 2016–2017 年逐時資料，並附建築中繼資料與天氣資料 [D3]。3,053 是各類計量表的總數，不是電表數。
- **技術：**
  - 以區間電表資料建立統計基準，在 M&V 研究中已有大規模驗證 [D11]。
  - LLM Agent 以「推理–動作–觀察」交替的方式呼叫外部工具 [A1]，已有研究把它用在建築自動化系統的時序查詢 [A4]。

## C. Problem（↔ H. However）

管理者看到「週末用電變高」時，仍需要自己判斷幾件事：比較的期間是否合理、氣溫是否不同、資料有沒有缺漏、下一步該查營運排程還是查電表。從圖表或異常分數走到可執行的調查，中間有一段需要領域判讀的工作。

> **本專題的研究問題：** 在只有建築總表、天氣與有限建築資訊的條件下，結合確定性分析工具、明示的領域規則與受限的 LLM 規劃，能否比固定報表或「固定流程＋LLM」產生**數值正確、證據完整且不過度推論**的調查建議？

這是待驗證的假設，不預先宣稱 AI Agent 優於既有方法。

## D. Existing Limitations（↔ H. However＋I. In literature＋J. Judgement）

既有方法大致依時間演進、由簡到繁（I）。每一列先評論該方法的限制（J），再說明本專題如何回應。

| 方法類別（由舊到新） | 代表證據 | 限制（Judgement） | 本專題的回應 |
|---|---|---|---|
| 固定門檻／人工看圖 | 本專題推論 | 天氣、營運與資料問題都可能觸發同一門檻，無法區分 | 以同星期×小時基準加上校準門檻；天氣只作為背景規則 |
| 統計／M&V 基準模型 | [D8][D11] | 能建立可靠的基準，但整棟總表無法驗證個別措施或設備 [D8] | 只回報「相對基準的偏離量」，不宣稱節電或根因 |
| 公開資料與清理流程 | [D3][D6] | cleaned 版本已把離群值與長段零值改為缺值，可能刪掉想研究的異常 [D6] | 以 raw 為主要輸入並加上品質旗標；cleaned 只作敏感度分析 |
| 異常偵測資料集與深度模型 | [D10][D13] | 需要標註；標籤是二元的，沒有說明「為什麼」或「下一步」 | 輸出五段式建議，不訓練新的偵測器 |
| 時序基礎模型 | [A8][D9] | 在建築的未見資料上只略優於統計模型 [A8]；本地調整與上下文長度會影響表現 [D9] | 最低版本採逐棟統計基準，基礎模型列為擴充 |
| LLM 直接判讀時序 | [A6][A5] | 明確推理不能改善偵測，也沒有證據顯示 LLM 能理解細微的真實異常 [A6]；AI 輔助產生的說明不等於物理因果 [A5] | LLM 不產生任何數值，數值一律來自工具 |
| 工具型 LLM Agent（建築／能源） | [A4][A7][A10] | 有查詢錯誤與遺漏 [A4]；能源分析類問題正確率 77% [A7]；66 篇研究中僅 4 篇達試點層級證據 [A10] | 工具白名單、呼叫預算、證據驗證與模板降級，並以三組比較驗證 Agent 是否有額外價值 |

## E. Innovation（↔ K. Keypoint）

本專題的創新定位是**「可追溯的調查流程」**，不宣稱發明新的異常偵測演算法，也不宣稱全球首創。

1. **職責分離：** LLM 只做需求解析、受限規劃，以及一次依觀察的規則選擇；數值、門檻與事件全部由可重現的程式產生，LLM 不能修改固定設定。
2. **證據契約：** 每個數值主張都綁定 evidence_id，並比對建築、期間、單位與數值，不能只檢查 ID 存在。驗證失敗就降級為固定模板。
3. **條件式領域規則：** 規則的前提不成立時自動停用（缺天氣就停用 weather_context，缺作息就停用 schedule_check），而不是讓 LLM 自行補造背景。
4. **五段式建議：** 觀察 → 基準 → 假說 → 尚缺證據 → 下一步查核。允許回答「資料不足以判定」。
5. **規格驅動：** 系統行為先寫成 OpenSpec 規格（9 個 capability），每個 Flowchart 分支都有可測的 Scenario。

## F. Contributions（↔ K. Keypoint＋L. List the organization）

**預期貢獻**（本階段尚未實作或證明）：

1. 一個以公開歷史電表重播的建築用電異常調查原型，用來驗證受限工具使用的可行性。
2. 一套保留品質旗標、來源、門檻與假設的證據格式，讓管理者能核對每一個數字與建議。
3. 一個公平的評估協議：B0／B1 基準、合成擾動敏感度，以及固定報表、固定流程＋LLM、受限 Agent 三組在 10 個固定案例上的比較。協議可以分離文字生成與規劃各自的效益。
4. 一份從 DESIGN.md 轉換而來的 OpenSpec 規格與對照表，讓下一位開發者可以逐條實作與驗收。
